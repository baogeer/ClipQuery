# ClipQuery 架构文档

> 版本：v0.3（与 `clipquery/` 当前实现对齐）
> 更新：2026-11-06

本文档是**开发者视角**的架构参考。面向需求和产品定位请看 [需求文档](./需求文档.md)。

## 1. 分层概览

ClipQuery 采用"离线准备数据、在线只做检索"的经典两段式架构，层内职责单一、层间以数据为契约。

```
┌───────────────────────────────── 接口层 ──────────────────────────────────┐
│  clipquery/api/main.py           FastAPI 端点                             │
│  + BackgroundTasks               入库异步任务（进程内队列）                 │
└────────────────────────────┬──────────────────────────────────────────────┘
                             │  调用
┌────────────────────────────▼──────────────────────────────────────────────┐
│  clipquery/search/retriever.py   在线检索                                  │
│  Retriever.search()              查询编码 → KNN → 聚合 → JOIN              │
└────────────────┬───────────────────────────┬──────────────────────────────┘
                 │                            │
┌────────────────▼───────────────────────────▼──────────────────────────────┐
│  存储层（三索引 + 对象存储）                                                │
│  ┌─────────────────────┐ ┌──────────────────────┐ ┌────────────────────┐ │
│  │ clipquery_frames    │ │ clipquery_clips      │ │ clipquery_articles │ │
│  │ (knn_vector + 帧元)  │ │ (片段元 + COS URL)   │ │ (info.json 副本)   │ │
│  └─────────────────────┘ └──────────────────────┘ └────────────────────┘ │
│  ┌──────────────────────────────────────────────────────────────────────┐ │
│  │ 腾讯云 COS: ClipQuery/<article_id>/{video.mp4|clips/*|thumbnails/*} │ │
│  └──────────────────────────────────────────────────────────────────────┘ │
└────────────────────────────▲──────────────────────────────────────────────┘
                             │  写入
┌────────────────────────────┴──────────────────────────────────────────────┐
│  clipquery/pipeline/   离线处理                                            │
│  ┌──────────────────────────────────────────────────────────────────────┐ │
│  │ extractor.py   OpenCV 抽帧（固定 FPS）                                │ │
│  │ clipper.py     PySceneDetect 场景切分 + ffmpeg 流 copy                │ │
│  │ encoder.py     CLIP 文本/图像统一编码（单例）                          │ │
│  │ indexer.py     编排：切片 → 编码 → 上传 → 三索引 upsert                │ │
│  └──────────────────────────────────────────────────────────────────────┘ │
│  scripts/         CGTN 爬虫（独立进程）                                     │
└────────────────────────────▲──────────────────────────────────────────────┘
                             │
                        （CGTN 网站）
```

## 2. 模块职责与边界

### 2.1 `clipquery.config` / `clipquery.paths`

**职责**：所有可变参数的唯一入口。`paths.py` 让项目完全不依赖绝对路径——部署时改 `CLIPQUERY_PROJECT_ROOT` 一个环境变量就行。

**边界**：
- 任何业务模块不要自己 `os.getenv()` 读配置。走 `from .config import settings`。
- `settings` 在 import 时就实例化并 `ensure_dirs()`，所以 import 本模块会产生一次目录创建副作用——测试里别 import。

### 2.2 `clipquery.cos`

**职责**：腾讯云 COS 对象存储的瘦封装。

**关键函数**：
| 函数 | 作用 |
|---|---|
| `get_cos()` | `lru_cache` 单例，首次调用建立连接 |
| `upload_file(local, key, skip_if_exists=True)` | 幂等上传，返回 https URL |
| `object_url(key)` | 纯字符串拼接，不发请求 |
| `exists(key)` | head_object 判空 |
| `article_key(aid, name)` | `ClipQuery/<aid>/<name>` |
| `clip_key(aid, cid)` | `ClipQuery/<aid>/clips/<cid>.mp4` |
| `thumbnail_key(aid, fid)` | `ClipQuery/<aid>/thumbnails/<fid>.jpg` |
| `upload_and_delete(local, key)` | 上传后立即 `unlink` 本地文件；失败保留本地便于重试 |

**失败策略**：上层捕获 `Exception` → 打 `[WARN]` → 落回本地路径（文件此时也不会被删）。COS 挂了不阻断主流程。

**本地不持久化**：除了 `video.mp4` 需要跨步骤复用（下载→切片→抽帧），其他所有文件（audio / srt / info / clip / thumbnail）都是"写盘仅为了喂给 SDK 上传"，完事即删。

### 2.3 `clipquery.pipeline.extractor`

**职责**：OpenCV 抽帧。`iter_frames(path, sample_fps, max_side)` 是生成器，按固定 FPS 抽，每帧 resize 到长边 384（节省 CLIP 显存），yield `Frame(video_path, frame_index, timestamp, PIL.Image)`。

**关键设计**：
- **不一次性读整个视频**。生成器 + 批次编码 = 显存占用恒定
- `frame_index` 用原视频帧号，`timestamp = idx / src_fps`，入库时直接存秒

### 2.4 `clipquery.pipeline.clipper`

**职责**：把视频物理切成可独立播放的 MP4 片段。

**流程**：
```
plan_clips(video) ──> _detect_scenes()   # PySceneDetect ContentDetector
                 \──> _normalize()       # 过长拆、过短并
                 \──> 失败时 _fixed_windows()  # 等长 6s 兜底

cut_clips() ──> for each (start, end):
                  _ffmpeg_cut()  # -c copy 优先，失败重编码
                → Clip(id, article_id, index, start, end, local_path)
```

**关键设计**：
- 片段 id = `sha1(article_id:start:end)[:20]` → 相同窗口重跑拿同一个 id，天然幂等
- `-c copy` 失败再 `libx264 veryfast` 兜底。前者秒级无损，后者兼容性好
- `+faststart` 让 moov 在前，浏览器可边下边播

### 2.5 `clipquery.pipeline.encoder`

**职责**：CLIP 文本 + 图像的统一编码。

```python
from clipquery.pipeline.encoder import get_encoder
enc = get_encoder()           # 全局单例，首次下载模型
enc.encode_text("sunset")     # (1, 512) float32 L2-normalized
enc.encode_images([pil_img])  # (N, 512)
```

**关键设计**：
- `sentence-transformers` 的 CLIP 封装，文本和图像自动在同一向量空间
- `normalize_embeddings=True` → 后面可以直接用点积/余弦
- `lru_cache` 单例：离线入库和在线查询共用同一个模型加载，省显存

### 2.6 `clipquery.pipeline.indexer`

**职责**：**编排器**——把切片、编码、COS 上传、三个索引的写入串起来。

**核心时序**：
```
ingest_video(video_path, article_id=None):
  0. 推断 article_id（视频父目录名）
  1. 幂等检查：vector_store.video_frame_count() > 0 → 跳过
  2. 读 article 元数据（从 clipquery_articles，爬虫已经写过了）
  3. _process_clips():
       cut_clips() → 本地 MP4
       for clip: upload_and_delete() → COS URL
       clip_store.upsert_many()
       rmtree(data/clips/<article_id>/)
  4. 抽帧循环:
       for batch in iter_frames():
         vecs = encoder.encode_images(batch)
         for frame:
           save_thumbnail() + upload_file() → COS URL
           clip_id = find_clip_for_timestamp(clips, frame.ts)
           metadatas.append({... clip_id ...})
         vector_store.add(ids, vecs, metadatas)
  5. vector_store.refresh()
```

**关键设计**：
- **幂等**：以 `vector_store.video_frame_count(video_path) > 0` 作为"这条视频跑过"的信号
- **先切后编**：帧和片段用 timestamp 关联，必须先有片段窗口才能给帧打 `clip_id`
- **COS 失败降级**：任何一步 COS 失败都只是 warn，不影响索引写入

### 2.7 `clipquery.storage.*`

三个 store 用同一个 OpenSearch client，mapping 各不相同：

| 索引 | 文档 id | 关键字段 | 主要查询 |
|---|---|---|---|
| `clipquery_frames` | `sha1(video_path:frame_index)[:20]` | `embedding` (knn_vector), `article_id`, `clip_id`, `timestamp`, `thumbnail` | KNN |
| `clipquery_clips` | `clip_id` | `clip_url`, `start_time`, `end_time`, `article_url`, `title` | `mget` by id |
| `clipquery_articles` | `article_id` | `url`, `title`, `paragraphs`, `cos_video_url` | `get` by id |

**关键设计**：
- **id 全部可推导、可幂等** → 重跑永远覆盖同一个 doc
- **元数据反范式化**：`clips` 里既存 `article_id` 也存 `article_url`、`title`。省一次 join，检索延迟更可预测
- **KNN 引擎**：nmslib + hnsw + cosinesimil，和 CLIP 的 L2 归一化向量天然匹配

### 2.8 `clipquery.search.retriever`

**职责**：在线检索的全部逻辑。

**流程**：
```
search(text|image_bytes, top_k):
  1. qvec = _encode_query()      # 文本/图片/混合 → 1 个 512d 向量
  2. hits = vector_store.query(qvec, candidate_k=top_k*5)
  3. 按 clip_id 聚合：同一片段保留最高分 hit
  4. clip_store.get_many()       # mget 拉片段元数据
  5. article_store.get()         # 拉文章元数据（反查 title/paragraphs）
  6. ClipSegment 装配 → 排序 → 返回 top_k
```

**关键设计**：
- **candidate_k = top_k × 5**：多召回、后聚合。因为同一片段里可能多帧命中，不多召回 top_k 会被同片段撑爆
- **返回 `ClipSegment` 而不是帧**：业务拿到就能直接放 `<video src=clip_url>`，不用再二次计算时间窗口
- **文章去重拉取**：几十个片段可能同属 3 篇文章，只发 3 次 `article_store.get()` 而不是逐片段拉

### 2.9 `clipquery.api`

**职责**：HTTP 接口。路由本身很薄，主要做请求校验、后台任务调度、结果序列化。

**端点**：
- `POST /ingest` 三选一：
  - `file`：上传 MP4
  - `path`：服务器本地绝对路径
  - `url`：CGTN 文章 URL，后台先爬再 indexer（延迟 import 爬虫，避免加载 whisper）
- `GET /ingest/{job_id}` 查询任务状态（queued / crawling / ingesting / done / failed）
- `POST /search`：文本/图片/混合
- `GET /health`

**特点**：
- `BackgroundTasks` 异步执行入库，返回 `job_id`
- `_JOBS` 是进程内 dict——**重启丢状态**。生产环境想要持久化需上 Celery/RQ
- **强制 `--workers 1`**：多 worker 下 `_JOBS` 不共享，查询 `job_id` 会随机 404
- Pydantic 模型 `SegmentOut` / `SearchResponse` 是对外契约，改动要兼容前端

### 2.10 `clipquery.website.cgtn` 爬虫核心

抓取/下载/落库的逻辑全部在这个子包里，和 scripts 入口完全解耦。未来接新来源（如新华社、CCTV）各自建 `website/<name>/` 子包，对外暴露同样的 `process_one_article(url) -> dict`。

- `transcript.py`：CGTN 列表/详情页 HTML 解析（XPath + JSON-LD + data-json 多路兜底）
- `video_downloader.py`：m3u8 → ts → mp4 两阶段下载，`tempfile.mkdtemp` 并发安全
- `pipeline.py`：单篇完整流程（抓页面 → 下视频 → ASR → 上传 COS → 写 `clipquery_articles`）

### 2.11 `scripts/` 入口

薄入口，只做参数解析 + 调 `clipquery.*`，不含业务逻辑。

- `crawl_one.py`：单 URL 抓取（只爬，不入库）
- `pipeline_one.py`：端到端（爬 + 切片 + 编码 + 三索引）
- `ingest_cli.py`：批量把 `news/` 下已有视频入库

## 3. 数据流详解

### 3.1 爬虫入库流程

```
crawl_one(url)
  │
  ├─ parse_transcript_detail(url)           # 拿 title/paragraphs/m3u8
  │
  ├─ article_id = sha1(url)[:16]
  ├─ article_dir = news/<article_id>/
  │
  ├─ article_lock(article_dir):              # 跨进程文件锁
  │   ├─ if info.json 存在: return 已有 meta
  │   │
  │   ├─ download_m3u8_as_mp4()              # m3u8 → mp4
  │   │   └─ tempfile.mkdtemp 独占 ts 临时目录
  │   │
  │   ├─ export_audio_mp3()                  # ffmpeg 抽 128k mp3
  │   ├─ Whisper → video.srt (or 段落兜底)
  │   │
  │   ├─ cos.upload_file(video.mp4)          # 留本地，等 indexer 用
  │   ├─ cos.upload_and_delete(audio.mp3)    # 上传 → 立即 unlink
  │   ├─ cos.upload_and_delete(video.srt)    # 同上
  │   │
  │   ├─ write info.json (atomic: .tmp → replace)
  │   ├─ cos.upload_file(info.json)          # 第一次上传
  │   ├─ cos_info_url 回填 meta，重写并再次上传覆盖
  │   ├─ os.remove(info.json)                # 本地也删
  │   ├─ article_store.upsert(article_id, meta)
  │   │
  │   └─ return meta  # 此时本地只剩 news/<aid>/video.mp4
```

**事务性**：
- 文件系统层：`os.replace` 保证 info.json 原子可见
- COS 层：单对象上传原子；多对象之间不是原子（上传中途失败可能出现 video.mp4 在但 audio.mp3 不在）
- OpenSearch 层：`upsert` 以 article_id 为主键，重跑覆盖

### 3.2 视频入库流程

```
ingest_video(news/<aid>/video.mp4)
  │
  ├─ article_id = _infer_article_id()        # 父目录名
  ├─ vector_store.video_frame_count() > 0 → skip
  │
  ├─ article_store.get(article_id)           # 读爬虫阶段写的元数据
  │
  ├─ cut_clips():                            # 场景检测或 6s 等长
  │   └─ 对每个窗口 ffmpeg -c copy 切 mp4
  │
  ├─ for clip:
  │   ├─ cos.upload_file(clip.local_path)    # ClipQuery/<aid>/clips/<cid>.mp4
  │   └─ 装配 clip_doc
  ├─ clip_store.upsert_many(clip_docs)
  │
  ├─ for batch in iter_frames(video, fps=1.0):
  │   ├─ vecs = encoder.encode_images(batch)
  │   │
  │   ├─ for frame:
  │   │   ├─ save_thumbnail() → data/thumbnails/<fid>.jpg（临时）
  │   │   ├─ cos.upload_and_delete()         # 上传后立即删
  │   │   └─ clip_id = find_clip_for_timestamp(clips, frame.timestamp)
  │   │
  │   └─ vector_store.add(ids, vecs, metadatas)  # bulk upsert
  │
  ├─ vector_store.refresh()
  │
  └─ shutil.rmtree(news/<article_id>/)       # 含 video.mp4，彻底归零
```

### 3.3 检索流程

```
POST /search  (query="一个人在海边奔跑", top_k=10)
  │
  ├─ Retriever.search():
  │   ├─ qvec = encoder.encode_text(query)   # (1, 512)
  │   │
  │   ├─ hits = vector_store.query(qvec, candidate_k=50)
  │   │     ↓ OpenSearch KNN DSL
  │   │     ↑ 50 个 hit（含 clip_id、article_id、thumbnail URL、score）
  │   │
  │   ├─ per_clip = {}
  │   │   for h in hits:  # 聚合，一片段留最高分
  │   │     per_clip[h.clip_id] = max(current, h)
  │   │
  │   ├─ clip_docs = clip_store.get_many(clip_ids)
  │   │     ↓ OpenSearch mget
  │   │
  │   ├─ article_docs = {aid: article_store.get(aid) for aid in unique_aids}
  │   │     ↓ OpenSearch get × 去重后的文章数
  │   │
  │   └─ 装配 ClipSegment × top_k
  │
  └─ SearchResponse(results=[
        SegmentOut(
          clip_url="https://cos.../ClipQuery/<aid>/clips/<cid>.mp4",
          article_url="https://news.cgtn.com/...",
          title="...",
          start_time=12.5, end_time=18.0,
          score=0.874,
          thumbnail="https://cos.../ClipQuery/<aid>/thumbnails/<fid>.jpg",
          paragraphs=[...]
        ), ...
     ])
```

## 4. 关键架构决策

### 4.1 为什么是三个索引而不是一个

**候选方案**：所有数据塞 `clipquery_frames`，用 `doc_type` 字段区分。

**选择三索引的理由**：
- **mapping 清晰**：knn_vector 很重，塞进 article 文档会浪费存储
- **查询模式不同**：frames 永远 KNN；clips 永远 mget；articles 永远 get by id
- **删除成本低**：想重建向量只需重建 `frames`，不碰文章和切片

**代价**：
- 检索链路 3 次请求（KNN → mget clips → get articles）
- 元数据冗余：`clips` 里存了 `article_url` / `title`，`articles` 里也有

### 4.2 为什么先切片再编码

**候选方案**：先编码所有帧，查询时再按命中帧动态切片。

**选择"先切片"的理由**：
- 查询响应延迟 < 500ms 的目标下，不能把 ffmpeg 切片放在请求路径上
- 前端拿到 `clip_url` 可以立刻 `<video src=...>` 播放，无需等后台产出
- 切片是预先付费（入库慢），换查询免费

**代价**：
- 入库时间翻倍（切片 + ffmpeg）
- COS 存储开销翻倍（原视频 + 切片）

### 4.3 为什么把 OpenSearch 向量和元数据存一起

**候选方案**：FAISS（纯向量）+ PostgreSQL（元数据）。

**选择 OpenSearch 的理由**：
- 公司已有 AWS OpenSearch 托管域（部署成本 0）
- `knn + filter` 组合查询直接支持（下一版做"按时间过滤"）
- 一次请求返回向量+元数据，避免两库往返

### 4.4 为什么异步入库但同步检索

**入库**：
- 视频抽帧 + CLIP 编码 10 秒以上，HTTP 不能同步等
- 用户只关心"任务入队"，`job_id` 轮询足够

**检索**：
- 全部内存操作，p99 < 500ms
- 异步徒增复杂度

## 5. 并发与一致性细节

### 5.1 爬虫并发语义（`clipquery/website/cgtn/pipeline.py`）

| 并发场景 | 机制 | 结果 |
|---|---|---|
| 同一 URL 多个进程同时跑 | `news/<aid>/.lock` 文件锁（msvcrt/fcntl） | 后者阻塞，双检 info.json 后直接返回 |
| 不同 URL m3u8 base 撞车 | `tempfile.mkdtemp(prefix=base)` | 各拿独占临时目录 |
| info.json 写入崩溃 | `write .tmp + os.replace` | 永远读到完整文件或空 |

### 5.2 向量入库并发

`ingest_video` 没有加锁。两个进程并发入同一视频会**双写**（重复做功但不脏数据——文档 id 幂等，覆盖写）。

**推荐做法**：外层调度器（Celery / cron）保证同一 video_path 只有一个 worker。

### 5.3 OpenSearch 读写一致

- 入库后 `vector_store.refresh()` 一次，保证"入库刚完成就查得到"
- `clip_store.upsert_many(refresh=True)` 同理
- 高吞吐场景可去掉 refresh，依赖默认 1s 刷新间隔

### 5.4 COS 幂等

`upload_file(skip_if_exists=True)` 会 head_object 一次。相同 key 第二次上传跳过。

**例外**：`info.json` 强制 `skip_if_exists=False`，因为可能需要更新字段。

## 6. 可观测性现状

**目前只做到**：
- `print()` 日志（带 `[WARN]` / `[ERROR]` 前缀）
- `tqdm` 进度条

**没有**：
- 结构化日志、trace、metrics
- 入库任务持久化、重试机制
- OpenSearch / COS 调用的耗时监控

详见 [需求文档 §9.3](./需求文档.md#9-未完成--下一阶段)。

## 7. 扩展点

想加新功能，应当从哪里改：

| 需求 | 改动点 |
|---|---|
| 换向量模型 | `clipquery/pipeline/encoder.py` + `config.embedding_dim` + 重建 `frames` 索引 |
| 加 Whisper 转录检索 | 新增 `transcripts` 索引 + 爬虫阶段跑完 Whisper 后入索引 + `retriever` 加文本检索分支 |
| 改片段切分策略 | `clipquery/pipeline/clipper.py` 替换 `_detect_scenes` 实现 |
